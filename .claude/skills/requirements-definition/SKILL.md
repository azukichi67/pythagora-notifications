# 要件定義

## 大原則

**要求をそのまま要件として書かない。**

| | 要求 | 要件 |
|---|---|---|
| 定義 | ユーザーの希望・願望 | システムが満たすべき条件 |
| 特徴 | 曖昧、主観的 | 具体的、検証可能 |
| 例 | 使いやすくしたい | 3クリック以内で目的の画面に到達できる |
| 例 | 早くしたい | 検索結果が2秒以内に表示される |

要求を引き出し、整理し、要件として定義する。このプロセス全体が要件定義である。

本プロジェクトは発注者と受注者が同一人物のため、要求を出すのも検証するのもユーザー本人になる。**だからこそ要求と要件の境目が消えやすい。** ユーザーの発言は要求であって要件ではない、という区別を Claude 側が保つ。

## 書き始める前に

### 前提が合意されているか確認する

要件は `concept.md`（解く課題・スコープ・やらないこと）と `domain.md`（用語・データモデル）の上に乗る。前提がズレていれば、書いた要件も全部ズレる。

着手前に確認すること。

- `docs/TODO.md` のフェーズ1に未チェック項目が残っていないか
- 残っていれば `requirements.md` に着手しない。未決事項をユーザーに提示し、決定を促す（後述の「決まらないとき」参照）

### 既存ドキュメントを転記しない

| 内容 | 置き場所 |
|---|---|
| 目的・課題・スコープ・やらないこと | `concept.md` |
| 用語・データモデル・モデル上の決定と根拠 | `domain.md` |
| 未決事項・作業予定 | `docs/TODO.md` |
| 機能・画面・非機能要件・制約条件 | `requirements.md` |

`requirements.md` からは参照するだけにする。転記すると二重管理になり、いつか食い違う。

## `requirements.md` の章立て

```
# 要件定義

## 制約条件・前提条件
## 機能要件
### 機能一覧
### ユースケース（複雑な機能のみ）
## 画面一覧
## 非機能要件
```

冒頭に `concept.md` / `domain.md` への参照を1行置く。

書かない章と、その理由。後から「なぜ無いのか」を再検討しないで済むように、理由ごと記録する。

| 一般的な要件定義書の章 | 本プロジェクトでの扱い |
|---|---|
| エグゼクティブサマリー | 書かない。読み手が1人で、要約を読ませる相手がいない |
| プロジェクト概要 | `concept.md` を参照 |
| ステークホルダー一覧 | `concept.md`「利用者」を参照 |
| 業務フロー図 | `concept.md`「利用シーン」を参照 |
| 帳票一覧 | 帳票は存在しない、と明記する |
| 用語集 | `domain.md`「用語」を参照 |

## 機能一覧

システムが持つ機能を漏れなく整理した表。

| 機能ID | 機能名 | 機能概要 | 優先度 | 関連画面 | 備考 |
|---|---|---|---|---|---|
| F-001 | 場所の登録 | 場所名を入力して `Place` を1件作成する | Must | S-002 | `name` 以外は任意 |

- 機能IDは `F-001` 形式。一度振った番号は再利用しない
- 機能概要は「何ができるか」を1文で。実装方法は書かない
- 関連画面は画面一覧のIDで参照する

### 優先度は MoSCoW で決める

| 分類 | 意味 | 割合の目安 |
|---|---|---|
| Must | なければ成り立たない | 〜60% |
| Should | ないと困るが、なくても最低限は動く | 〜20% |
| Could | あれば嬉しいが、なくても許容範囲 | 〜20% |
| Won't | 今回はやらない | - |

**Must が6割を超えたら、優先順位がついていないと考える。** 「全部必須」は「優先順位なし」と同じ。

ユーザーが全部 Must にしようとしたら、トレードオフを数字で見せて判断を促す。

- 「この機能を足すと、動くものが見えるまで◯日遅れます。それでもいいですか？」
- 「Must を3つに絞るとしたら、どれを残しますか？」

Won't に落とした機能は `concept.md`「やらないこと」または `docs/TODO.md`「劣後」に移す。`requirements.md` には残さない。

## ユースケース

複雑な機能だけ詳細化する。単純な CRUD には書かない。

| 項目 | 内容 |
|---|---|
| アクター | 誰が使うか |
| 事前条件 | この機能を使う前の状態 |
| 基本フロー | 正常な流れ |
| 代替フロー | 分岐する場合の流れ |
| 例外フロー | エラーの場合の流れ |
| 事後条件 | この機能を使った後の状態 |

**例外フローが埋まらない機能は、要件が固まっていない。** 後述の「例外を引き出す」を先にやる。

## 画面一覧

| 画面ID | 画面名 | 概要 | 関連機能 |
|---|---|---|---|
| S-001 | 場所一覧画面 | 登録済みの `Place` を全件表示する | F-003 |

画面は「利用シーンの一部を切り取ったもの」。`concept.md` の利用シーン（閲覧＝出発直前・スマホ／記録＝出先または帰宅後・スマホ）の各場面で「何をするか」を考えると、必要な画面が洗い出せる。

### 文章だけでは認識がズレる

同じ言葉が別物を指す。`requirements.md` にこれらの語を書くときは、必ず具体化する。

| 文章での定義 | 解釈A | 解釈B |
|---|---|---|
| 一覧表示 | 10件ずつページング | 全件を無限スクロール |
| 検索機能 | テキストボックス1つ | 日付・ステータス等の複合検索 |
| 編集可能 | 別画面で編集 | 一覧上で直接編集（インライン） |
| ステータス表示 | テキストで「承認済」 | 色付きバッジでアイコン表示 |

文章で書けば「一覧表示」の5文字で済むが、実装するには決めることが100個ある。決まっていない項目は Claude が実装時に勝手に決めることになる。

画面モックが必要になったら、要件定義段階ではローファイ（グレー中心の大まかなレイアウト）で止める。きれいに作ると色やデザインの議論になり、「何を置くか」が決まらない。

## 非機能要件

機能要件が「何をするか」なら、非機能要件は「どのくらいのレベルで」。6カテゴリすべてに言及する。検討した結果「不要」なら、不要と書く。

| カテゴリ | 内容 |
|---|---|
| 可用性 | どのくらい止まらないか |
| 性能 | どのくらい早いか |
| 拡張性 | 将来の拡張に対応できるか |
| 運用保守 | 運用しやすいか |
| 移行性 | データ移行できるか |
| セキュリティ | 安全か |

### 「普通でいい」で済ませない

『普通』の定義は人によって違う。数値か、検証可能な条件で書く。

### 「当たり前」こそ明文化する

書いていないものは、実装時に「やらなくていい」と解釈される。

- 日本語で表示される
- ブラウザの戻るボタンが使える
- スマートフォンの画面幅で横スクロールが出ない
- タイムアウトしたら再ログインが必要

### 全部を最高レベルにしない

システムの特性に合わせてメリハリをつける。本プロジェクトは家族向け・登録50件規模・停止しても誰も困らない。可用性やスケーラビリティに高い水準を置く理由がない。**高い水準を置かないと決めたことも、決定として書く。**

## 曖昧な言葉は、後で揉める言葉

| 悪い例 | 問題点 | 良い例 |
|---|---|---|
| 使いやすくする | 基準がない | 3クリック以内で完了 |
| 早くする | 測定できない | 応答時間2秒以内 |
| たくさん保存できる | 曖昧 | 10万件まで保存可能 |
| 場所を管理できる | 範囲が不明 | 登録・編集・一覧表示ができる（削除はしない） |

受発注の現場なら揉める相手は顧客だが、本プロジェクトでは**未来の自分と、実装するときの Claude** が相手になる。曖昧な要件は消えてなくならず、実装時に誰かが勝手に決める。

「〇〇みたいに」という表現が出たら必ず具体化する。「Excel みたいに」は一覧編集・計算・コピペ・自由なレイアウトのどれを指すか分からない。

## 例外を引き出す

要件の抜け漏れは、ほぼ例外ケースで起きる。例外は「滅多に起きない」が「起きたら致命的」。しかもユーザーにとっては当たり前すぎて、聞かれないと言わない。

Claude 側から質問して引き出す。

| 質問 | 引き出せる例外 |
|---|---|
| 同じ場所を二重に登録したらどうしますか？ | 重複チェックの要否 |
| 間違えて「行った」を押したらどうしますか？ | 訪問の取消フロー（`Visit` は更新・削除しない方針との整合） |
| 登録が0件のときは何を表示しますか？ | 空状態の表示 |
| 必須項目を空のまま保存しようとしたら？ | バリデーションとエラー表示 |
| 通信が切れている出先ではどうなりますか？ | オフライン時の挙動 |
| 場所名が長いときはどう表示しますか？ | 折り返し・省略の扱い |

## 決まらないとき

**「あとで決めましょう」を受け入れない。** 理由は以下。

- 実装開始後は、決めている余裕がない
- 他の機能との整合性が取れなくなる
- 後から決めると手戻りが発生する
- 結局決まらず、実装時に Claude が勝手に決める

### 決断を促す

ユーザーが決められないときは、決められない理由に合わせて対処する。

| 決められない理由 | 対処 |
|---|---|
| 情報が足りない | 選択肢と、それぞれの影響を整理して見せる |
| 判断材料がない | 最悪ケースと、その場合の対策を説明する |
| どちらでもよく見える | 差が出る具体的な場面を1つ挙げる |

問いかけの型。

| テクニック | やり方 |
|---|---|
| 選択肢を絞る | 「A・B・Cの3案があります。どれにしますか？」 |
| デフォルトを提示 | 「特に指定がなければAで進めますが、よいですか？」 |
| リスクを伝える | 「決まらない場合、この部分の実装が止まります」 |
| 仮決定にする | 「一旦Aで進めて、◯◯の時点で見直しましょう」 |

**仮決定には必ず見直し時点を書く。** 「いつか見直す」は見直されない。

### 未決事項は TODO.md へ書き戻す

それでも決まらなければ、`requirements.md` に空欄で残さず `docs/TODO.md` に以下の形式で書く。空欄は「決まっていない」ことを伝えず、読み飛ばされる。

- 何が決まっていないか
- いつまでに決める必要があるか（どの作業の前か）
- 誰が決めるか
- 決まらなかった場合のリスク
- 仮の前提（あれば）

## 書き終えたら

自己レビューしてからユーザーに出す。

- 用語は `domain.md` と統一されているか（`Place` / `Visit` / 最終訪問日 / 予算帯 / 雨天可）
- 機能間で矛盾はないか
- 抜け漏れはないか（特に例外ケース）
- 実現可能性に問題はないか
- 曖昧な表現を排除したか
- `concept.md`「やらないこと」に該当する機能が混入していないか
- Must が6割を超えていないか

ユーザーの合意を得たら、`docs/TODO.md` から該当項目を消して `requirements.md` へ移す。合意した内容と、その根拠を残す。後から蒸し返さないための記録になる。

## やってはいけないこと

| アンチパターン | なぜダメか |
|---|---|
| とりあえず実装して見せる | 家を建ててから「3階建てにして」と言われるのと同じ。手戻りのコストは工程が進むほど跳ね上がる |
| `concept.md` / `domain.md` の合意前に要件を書く | 前提がズレていれば、書いた要件も全部ズレる |
| 「あとで決めましょう」を受け入れる | 結局決まらず、実装時に勝手に決まる |
| 例外ケースを「起きてから考える」 | 本番で発覚したときの修正コストが跳ね上がる |
| 全機能を Must にする | 優先順位をつけていないのと同じ |
| 「やらないこと」の蒸し返しを合意なく受ける | スコープクリープ。「これくらいなら」の積み重ねで破綻する。追加したいなら、影響を示して `concept.md` を正式に更新する |
| 曖昧なまま先へ進む | 曖昧な言葉は、後で揉める言葉 |
